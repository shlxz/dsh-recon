## 2 检查 2：六通道的路由顺序

**方法**：用 `override` 强制走每条通道，观察实际行为

**结果**：❌ **发现缺陷 1 — override 跳过取证**

强制走 `read_trace` 时输出：

```
**建议通道** 读轨迹
**置信度** ██░░░░░░░░ 0.15
**已有证据** 无
```

——空证据、低置信度、**且没有说明原因**。

**根因**：`router.js` 的 override 分支在任何 `probe` 之前就 `return`：

```js
if (input.override) {
  return finalize(strategy, {...})   // ← probe 从未发生
}
```

**为什么严重**：override 的语义是"强制选择通道"，不是"跳过这条通道的工作"。返回一张空白卡片**看起来成功**，比正常路由更有害——使用者会以为通道查过了但没有结果。

**修复**：强制通道仍然执行它自己的 probe；证据通道之前的通道不跑（这才是"强制"的含义）。

**验证**：新增 3 条测试，变异回旧代码 → 3 项变红。

## 3 检查 3：闸门是否真的按经济性决策

**方法**：遍历 3 级 reversibility × 3 级 blast_radius × 2 种用户状态 = 18 种组合

**结果**：❌ **发现缺陷 2、3 — 量纲错配，闸门几乎恒判"打断"**

### 3.1 修复前的分布

```
假设: 4 / 18   （且集中在 "忙碌" 一侧）
```

### 3.2 三层根因

**根因 A：两笔账的标度不匹配**

| 账本 | 取值范围 |
|---|---|
| assumptionCost | 0.65 ～ 2.15 |
| interruptCost | 0.25 ～ 1.15（修复前） |

interrupt 的最大值**低于** assumption 的中位数，等于`打断永远更便宜`。

**根因 B：clamp 值过低，吞掉折扣**

`gatelessAssumption` 原为 `1.0`，而最贵的 base 是 2.15。后果：

```
blast=local   assume=1.0  raw=1.35  clamped
blast=module  assume=1.0  raw=1.60  clamped
blast=system  assume=1.0  raw=2.05  clamped
```

三种 blast 半径**输出同一个数字**；带证据时 2.05 打 43% 折得 1.17，仍被压回 1.0 —— **证据折扣完全失效**。

**根因 C：空闲项权重过大**

`W_IDLE 0.2` 对 `W_BASE_INTERRUPT 0.25`，等于 80% 折扣。用户空闲超 15 分钟后：

```
interrupt = 0.10
```

低于最低的 assumption（0.65）→ **任何决策都值得问**，包括"这个按钮用什么颜色"。

### 3.3 修复

| 参数 | 原值 | 新值 | 理由 |
|---|---|---|---|
| `gatelessAssumption` | 1.0 | **3.0** | 必须高于最贵的 base（2.15），否则差异被抹平 |
| `INTERRUPT_SCALE` | 无 | **2.0** | 把 interrupt 抬到与 assumption 同一区间 |
| `W_BASE_INTERRUPT` | 0.25 | **0.5** | 抬高空闲时的下限 |
| `W_IDLE` | 0.2 | **0.08** | 空闲只是"不那么打扰"，不是"免费"（占 base 16%） |

### 3.4 修复后的分布

```
忙碌时：8/9 选假设（仅 low/system 这种最贵决策才打扰）
空闲时：1/9 选假设（high/local 改按钮颜色这类，即使闲着也不问）
```

新增 4 条测试锁定这个分布，并用变异测试验证（回退 `INTERRUPT_SCALE` → 变红）。

> **一处自我纠正**：我曾断言"`W_IDLE 0.2` 是缺陷"，实测在 `base 0.5` 下 0.2 ≤ 0.25 属健康值，测试通过是对的。真正的病根是 `base 0.25` 配 `idle 0.2` 这个**比值**，不是 idle 本身。

## 7 检查 7：词法推断路径

**方法**：不声明枚举，让路由器自己推断

**结果**：❌ **发现缺陷 4 — 台账证据重复计入**

卡片证据区出现两条**完全相同**的记录：

```
- constraint 此前已按「read_trace」处理
- constraint 此前已按「read_trace」处理
```

**根因**：`trace.js` 取最近 2 条同 gap_type 的台账记录，但两条可能**断言同一个事实**，各计 0.25 权重 → coverage 虚高 → 置信度虚高。

**修复**：按事实文本去重，而不是按行去重。

**验证**：新增测试（同一事实两次 → 只 1 条；不同事实 → 都保留），变异回旧代码 → 变红。

## 10 关键状态：运行实例与源码不一致

**这是本次检查最重要的运维发现。**

| 事实 | 说明 |
|---|---|
| 源码 | 已含缺陷 1–4 的修复，89 项测试全绿 |
| 运行实例 | **仍是修复前的代码** |
| 证据 | 第 2、3、7 节的缺陷现象全部来自**真实调用**，说明运行的是旧版 |

**结论**：本报告的缺陷已在源码修复，但**尚未在真实运行环境验证**。

**没有一个是测试发现的。** 全部来自：
