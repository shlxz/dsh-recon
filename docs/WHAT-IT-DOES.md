# dsh-recon：它做了什么、有什么用、往哪走

> 写于 2026-11-07。作者是这个插件的实现者，以下内容是自我评估，不是产品介绍。
> 版本 `0.2.2`，115 项测试。文中每条判断都尽量标注证据来源。

---

## 一、它到底做了什么

### 1.1 一句话

**它在模型「准备向用户提问」之前插了一步，判断这一问值不值得。**

### 1.2 实际的一次调用

输入：

```
gap_type: goal
decision_at_stake: 贪吃蛇的形态
assumed_value: 单文件 HTML，键盘操控，无音效
user_state: { busy: false, idle_seconds: 300 }
```

输出（实测，1802 字符 JSON / 351 字符卡片）：

```
### 🛰 dsh-recon · 策略卡
**缺口** 目标 ｜ **建议通道** 先假设并标注
**置信度** ████████░░ 0.8
**按此假设执行** 单文件 HTML，键盘操控，无音效
**交付物里标注** ⚠ 待确认（goal）：贪吃蛇的形态
```

### 1.3 它真实计算的两个数

| 账本 | 组成 | 例子（上题） |
|---|---|---|
| `assumptionCost` | 可逆性权重 + 影响面权重 + 该缺口类型的先验风险 | 0 + 0.05 + 0.6 = **0.65** |
| `interruptCost` | 基础成本 + 忙闲 + 刚被纠正过 − 空闲减免，再乘缩放 | (0.5 + 0 − 0.066) × 2 = **0.868** |

`0.65 ≤ 0.868` → 假设更便宜 → **禁止提问**。

### 1.4 它没有做什么

| 它不做 | 说明 |
|---|---|
| 不问问题本身 | 六个通道里只有 `structured_form`/`minimal_question` 会真问，且默认 `mode:'plan'` 下不会自动执行 |
| 不选方案 | 具体做什么由模型通过 `assumed_value` 提供 |
| 不做安全判断 | 不扫代码、不判命令危险 |
| 不存记忆 | 台账在内存里，默认不落盘 |
| 不监听环境 | `query_sensor` / `read_multimodal` **是占位**，只探测工具是否存在，从不执行 |

> **这一条必须放在前面**：六个通道里有 **2 个是空的**。写报告时如果只看"六通道"这个名字，会高估它。

## 二、有什么用

### 2.1 解决了什么真实问题

**场景**：你对 AI 说"做个贪吃蛇"。

- **没有这个插件**：AI 直接开写，默认单文件 HTML 无音效。你可能要 HTML 或想加音效，于是**返工**。
- **有这个插件**：AI 先调 `route_info_gap`，算出"这决策可逆、影响面小、你在忙" → 该假设，于是带着"单文件 HTML，键盘操控，无音效"开工，并在交付里标注 ⚠。

**两者的区别不是"问或不问"，而是"用哪个默认值开工，以及这个默认值是否被明确标注"。**

### 2.2 它的三个真实价值

**① 把"要不要问"从直觉变成可复核的计算**

模型判断该不该问，是隐式的、不可追溯的。recon 输出 `assume=0.65 vs interrupt=0.868` —— 你可以指着这个数字说"这个判断错了"，而模型的直觉你只能接受或推翻。

**② 让"不该问"有一个具名结果**

`assume_and_flag` 不是一个状态，是一个指令：**别问，按这个做，并标注**。没有它，模型面对模糊需求只有两个默认行为：要么问，要么沉默地猜。后者更糟——**猜错且没标注**。

**③ 纠正归因**

每次决策有 `decision_id`，被纠正后 `corrected=true`，同类缺口累计 `prior_failures`。这给出一个可测的指标：`correction_rate`。

### 2.3 它不该被用在什么地方

**（这是我认为最重要的一节）**

| 场景 | 为什么不该用 |
|---|---|
| 高频琐碎交互（改个变量名、加一行日志） | 一次调用 1802 字符返回 + 3 次 probe，收益远小于成本 |
| 需要极低延迟的对话 | 每次多一轮工具调用 |
| 安全/合规判断 | 它不算这个，别指望 |
| 已明确的任务 | 没有缺口可路由 |

## 三、在哪些场景真的有用

按**实测数据**排序，不是按设计意图。

### 3.1 有用（有实证）

| 场景 | 证据 |
|---|---|
| **从零做一个小成品**（游戏/页面/脚本），形态未定 | 你实测报告：贪吃蛇 → 调用了，判 `assume_and_flag` |
| **用户只说"优化一下"** | 缺口类型 `goal` + 高可逆 + 低影响面 → 判假设，开工并标注 |
| **决策不可逆/影响大** | 实测：`删生产库`（`low/system`）→ `assume=2.15 > interrupt=2.1` → **判打断**，走 `structured_form` |
| **要动不熟悉的代码库** | `read_trace` 会读会话里已有的纠正记录（"不要用 moment.js"），命中即不再问 |

### 3.2 可能有用但未验证

| 场景 | 缺什么 |
|---|---|
| 长会话中的偏好收敛 | 需要真实使用数据，现在只有 8 条人工构造记录 |
| 团队协作中"谁的约定优先" | 未设计 |

### 3.3 无用或负作用

| 场景 | 后果 |
|---|---|
| 简单问题 | 实测：**一个按钮颜色问题也会依次探测 3 条通道**（`read_trace → query_sensor → read_multimodal`），全空后才假设 |
| 模型不懂 `assumed_value` 的场合 | 0.2.1 时出现过：判 `assume_and_flag` 后把问题原样退回，用户看到的是一句伪装成决定的提问 |

## 四、真实的代价（含批评的核对）

### 4.1 我认为成立的批评

| # | 批评 | 核对结果 |
|---|---|---|
| 1 | 固定流程开销 | **成立**。实测简单问题走 3 条通道 |
| 2 | 提示词 token | **成立且低估**。批评说 220，实际 **286**（0.2.2 加了 `assumed_value` 说明） |
| 3 | "为流程而流程" | **成立**。你报告的退回现象就是流程产物，我用 `assumed_value` 打补丁缓解，但没减少流程 |
| 4 | 宿主版本脆弱 | **成立**。`engines.dsh: >=0.2.1-rc.5 <0.3.0`，0.3 一出即装不上 |
| 5 | 过度设计 | **部分成立**。见 4.3 |

### 4.2 我认为不成立的批评

| 批评 | 为什么 |
|---|---|
| "代价比较依赖文本模式匹配，可能被别名/拼接绕过" | **代价来自显式枚举，不是文本**。代码顺序 `declReversibility ?? inferred.reversibility` —— 声明优先，词法只是兜底且 rationale 标注 `(inferred)`。这个插件不扫代码、不判命令，"绕过安全性检查"那套攻击面不适用 |
| "像 dsh-web-recon 只支持 0.1.x" | 那是另一个插件。本插件在真实 DSH 0.2.1-rc.5 上装过、跑过、多轮验证过 |

### 4.3 最根本的问题（我自己也认同）

> 它试图用一个结构化的外部流程，去规训一个本应灵活的内在判断。

代码级证据：

- `assumptionText()` 原本只能产出 **"按最小可逆的方案先做"** —— 一句不指名任何方案的空话
- 因为**路由器不知道正确答案**。它算得出"该假设"，算不出"假设什么"
- 所以我不得不把"假设什么"外包给模型（`assumed_value`）

**这个插件本质上是把判断拆成两半：该不该问（插件算）+ 具体怎么做（模型给）。** 拆分本身合理，代价就是你说的这层流程。

## 五、怎么改进

按**性价比**排序，不是按工作量。

### 5.1 立即可做（成本低，收益明确）

**① 廉价决策跳过侦察**

现状：`assume=0.65` 已经远低于 `interrupt=2.1`，仍要探测 3 条通道。

改法：进证据通道**之前**先算一次闸门。初始假设已明显更便宜（如 `assume < interrupt × 0.5`）→ 直接 `assume_and_flag`，零 probe。

- 收益：简单问题从 3 次 probe → 0
- 风险：可能漏掉真实痕迹。用**保守阈值**（只在差距很大时跳）+ 配置项
- 预期：这是最能缓解"流程过重"的一条

**② 缩减提示词**

286 token → 目标 180 以内。删掉重复说明，只保留触发条件。

- 已有限制：测试里有 `< 400 token` 的断言
- 风险：触发率可能下降，**必须实测**

**③ 明确能力边界**

在提示词和 README 里写清"本插件只做路由，不做安全判断、不选方案、不监听环境"。避免被误用。

### 5.2 中期（需要真实数据）

**④ 收缩为"两通道"版本**

现在的六通道里 2 个是空的、2 个只是调平台 API。真正的差异化只有 `read_trace` 和 `assume_and_flag`。

可以把六通道**降级为内部实现细节**，对外只暴露两种结果：
- "按这个假设做"（带 `assumed_value`）
- "问这一句"（带已知上下文）

`query_sensor`/`read_multimodal` 要么真正实现，要么从文档里删掉。**留着占位通道比删掉更有害**——它让人以为能力比实际大。

**⑤ 用真实数据校准阈值**

现在 18 种组合的分布（忙碌 8/9、空闲 1/9）是我**手调**出来的。真实应该由你的纠正率决定。

## 六、怎么转型（三个方向）

### 方向 A：收缩成"提问守门员"

**做什么**：只保留 `assume_and_flag` 的判定 + `assumed_value` 校验。删掉六通道叙事。

**优点**：
- 提示词可缩到 ~100 token
- 逻辑简单到不会误判
- 直接解决你遇到的核心痛点

**缺点**：放弃"先查痕迹再问"这个最有意思的部分

**适合**：你主要痛点是"AI 乱问"或"AI 闷头猜"

### 方向 B：扩张成"证据聚合器"

**做什么**：真正实现 `read_trace` / `query_sensor`，让它能读 git 历史、读现有代码约定、读端口状态。路由器从"该不该问"升级为"**能查到多少**"。

**优点**：这才是"侦察"名副其实

**缺点**：
- `query_sensor` 需要与每个传感器插件对参数契约，成本高
- 又回到 DSH 接口不稳定的问题

**适合**：你确实希望 AI 自己去看代码库，而不是问你

### 方向 C：退出插件形态，做成"提示词模式"

**做什么**：不做插件，只发一段 system prompt + 一个 JSON schema，让用户自己贴进 AGENTS.md。

**优点**：
- 零安装、零版本兼容问题
- 零固定流程开销（没有工具调用）
- 完全规避 DSH 生态脆弱性

**缺点**：没有台账、没有面板、没有纠正归因、不可观测

**适合**：如果你觉得这东西的价值主要是"提醒 AI 别乱问"，那它本来就不该是个插件

## 七、我的建议

**先做 5.1 的 ①②③（一天工作量），再用真实使用数据决定 A/B/C。**

理由：

1. **现在下判断数据不够**。台账只有 8 条，且全是我为验证构造的。你那次贪吃蛇是**唯一一次真实使用**，而它暴露了一个设计缺陷（模型把问题退回）。
2. **5.1 能立刻降低"流程过重"的批评**，且改动小、可回退。
3. **A/B/C 的选择取决于你实际痛什么**：
   - 痛"乱问" → A
   - 痛"不知道去查" → B
   - 觉得插件太重 → C

**我偏向 A 和 C 的组合**：把核心判断（该不该问 + 必须给具体假设）做成一段提示词，插件形态只作为"想要台账和面板的人"的可选增强。

**理由**：现在这个插件 2719 行源码、115 项测试，支撑的却是一个可以写进 200 字提示词的判断。**投入和产出不匹配。**
